- **Old links and browser camera code:** `/phone` returns 200 with the setup page; it is served directly, not an HTTP redirect, and that is fine. No `getUserMedia` remains in `static/`. `setup.js` has no `innerHTML` sinks, so stream error text is rendered with `textContent` only.
- **Auth matrix** (no token / display token / wrong token): every POST route, including `/api/camera/source` and `/api/camera/test`, returns 401 for all three. `/api/image` and `/api/calibration/image` return 401 for all three. `/api/state` accepts only the display token or the controller token.
- **Credentials:** a source of `http://admin:s3cret@…` appears in `/api/state` as `admin:***@`. `s3cret` does not appear in either the display or the controller response.
- **SSRF:** judged proportionate for a home-LAN app. Only a controller-token holder can reach `/api/camera/test` and `/api/camera/source`. Only `http(s)`, `file:` and `dir:` are accepted; `gopher:` and `ftp:` are refused. Only a decodable JPEG ever comes back, through `/api/image`. The remaining leak is an error oracle (HTTP status code, refused or timed out), which lets someone probe the LAN. With `file:` or `dir:`, any image on the Mac can be shown to the controller. Both are acceptable, because the controller is the owner.
- **README quickstart:** 10 steps. Every flag (`--camera` with the bare-IP shorthand, `--port`, `--lan-ip`, `--https`) and every UI label it names exists. The `tests/fake_ipwebcam.py --port 8080` rehearsal command works.

## Defects, by severity

**D1 — Medium. Confirming a camera dart commits whatever proposal is current at the moment of commit.**
- Where: `server.py:209-215`.
- The worker now replaces `vision.proposal` at up to 15 fps with no revision bump. A host tapping Confirm can therefore commit a dart other than the one on screen.
- The plan assigns the fix (`proposal_id`) to M1-10. It must land before auto-commit (owner decision #1).
- This is not a regression in kind: frames used to be pushed at a similar rate.

**D2 — Low/Medium. One boundary format yields no frames and no error.**
- Where: `camera_source.py:313,317`.
- If the header declares `boundary=--X` and the body uses the RFC form `----X`, the parser never matches a part. The setup page then sits on "Waiting for the first image…" with no error.
- Parsers in the wild disagree on the leading dashes; VLC had to patch for this ([vlc-devel](https://mailman.videolan.org/pipermail/vlc-devel/2012-August/089942.html)). I could not confirm DroidCam's exact framing.
- Fix: accept both `--`+b and `--`+`--`+b, or treat any line starting with the boundary text as a part start. Also raise an error after N KB with no part.

**D3 — Low. `/api/next` and the proposal checks read live Vision fields while the published state can show something else.**
- Where: `server.py:210,219`, with `vision.py:197`.
- `align()` calls `invalidate()` part-way through, but the snapshot is published only at the end. `/api/state` keeps showing `ready` while `/api/next` already sees `verified=False` and returns 400 "Reconnect camera…".
- I reproduced this with a delayed align. With a normal align the window is about 0.1–0.2 s.
- Fix: either read the same snapshot `/api/state` uses, or accept it as harmless (the user retries).

**D4 — Low. Queued actions can starve frame ingestion.**
- Where: `vision_worker.py:189-194`.
- The run loop works through every queued job before it processes one frame.
- In my 4-thread stress test, `processed_fps` fell to 0.0 and the frame age reached 2.0 s. If it reached 5 s, the next `ingest()` would invalidate calibration ("Camera reconnected").
- It is not realistic with 1–2 clients. Fix: run at most one job per loop pass, or ingest between jobs.

**D5 — Low. A POST to `/api/camera/source` without a `uri` key disconnects the camera.**
- Where: `server.py:136`.
- `body.get('uri')` returns `None` when the key is missing, and `None` means "disconnect".
- Fix: require `'uri' in body`.

**D6 — Low. Passwords that need percent-encoding fail.**
- Where: `camera_source.py:226`.
- `urlsplit().password` is not unquoted, so a password typed as `p%40ss` is sent literally and `@`, `/` and `#` cannot be used.
- Fix: `urllib.parse.unquote` the username and password.

**D7 — Low. Two paths take `vision.lock` on the HTTP thread with no timeout.**
- Where: `server.py:111` (`/api/calibration/image`) and `server.py:187` (proposal commit).
- Both bypass the worker's 10 s timeout and 503 path. The calibration image is the more questionable of the two.

**D8 — Low. Source switching is not serialised.**
- Where: `vision_worker.py:123` and `server.py:48-62`.
- `set_source()` swaps `self.source` with no lock. Two concurrent switches could both stop the same previous source and leak the other new one, along with its thread and socket.
- It did not happen in 40 concurrent switches, but a `threading.Lock` around `set_camera_source` is cheap.

**D9 — Low. `/api/camera/source` returns while the old source is still stopping.**
- `stop()` waits up to 2 s for the thread to join (switching away from a stalled stream took 3.0 s in total). A blocked `recv` is not interrupted by `response.close()`, so the old thread can outlive the join by up to the 3 s read timeout.
- It always exits in the end; no leak was observed.

**D10 — Nit. Smaller issues:**
- `redact_url` drops the brackets around IPv6 hosts (`camera_source.py:75`).
- Remote-controlled text (for example a `BadStatusLine` line) is echoed in `source.error` to display-token holders. It is safely rendered as text.
- `urllib` follows the macOS system proxy settings. A LAN camera could be routed through a configured proxy; `ProxyHandler({})` in `open()` (`camera_source.py:235`) avoids this.
- A failed decode is retried on every worker wake until a new frame arrives.

## Notes

**N1. The 7-action count assumes the source was set on the command line.** The test starts the server with `--camera dir:…`, so the source is already connected. Starting from an empty page, the flow is: type IP, Test, Connect, Freeze, 4 clicks, Verify. That is 9 actions, or 8 without Test. This meets the plan's intent when the README's `--camera` quickstart is followed.

**N2. Source switches do not bump the revision.** `/api/camera/source` checks `expected_revision` but does not increment it, so other controllers get no 409 after a switch. This belongs to M1-10's write-hardening scope.

**N3. HTTP on the LAN means tokens travel in clear text.** This is an accepted risk under owner decision #7, and the README states it clearly.
