## Defects, by severity

### Q1 — High (M1-11). The widened hit rings record scores that differ from the visible board.

- **Where:** `static/board.js:11-12` (`HIT_BULL=16`, `HIT_OUTER_BULL=40`, `HIT_BANDS` T 99–132, D 182–220). The visual rings stay at bull 7, outer bull 18, treble 113–122, double 184–194.
- **What happens:** the host taps where the dart *visibly* landed, but the invisible hit layer decides the score.
- **Measured** at 360×740 with real touch taps (`m1d_tap.cjs`). I sampled the SVG at 0.5-unit steps and compared each point's visible region with the hit element under it:
  - **20.5 % of the visible board records a different score.**
  - Outer-bull ring: **about 75 % of it records Bull 50.** A tap on its visual centroid (r=12.5) recorded 25×2.
  - Inner single: about 34 % records T or 25. A tap at r=108 (visible S20, 5 units inside the treble wire) recorded T20. A tap at r=30 (visible S20) recorded 25.
  - Outer single: about 16 % records T or D. A tap at r=127 (visible S20) recorded T20.
- **Why the tests pass anyway:** `qa_tap_board.cjs` taps each hit region's own `data-target` point, not the visual centroid. So acceptance #1 passes by construction.
- **Fix:** draw the tap board's picture with the same radii as the hit layer (an enlarged schematic board on `/control` only; `/play` keeps `markup()`). Or shrink the hit bands so that each hit region equals its visual region. Add a test that taps visual centroids and wire-adjacent points.
- **Related (Low):** a layout shift under the finger records a wrong region. In a manual game, an update from another controller inserts the "Match updated" notice above the board, and the board moves down. During my first probe run, a tap aimed at S20 recorded S3.

### Q2 — High (M1-14 / M1-12). A failing event-log write leaves a half-applied game write. Auto-commit then records the same dart up to 3 times.

- **Where:**
  - `camera_flow.py:102-109`: `EventLog.add` calls listeners without isolating their errors.
  - `recorder.py:134-145`: `append` lets `OSError` escape.
  - `server.py:298-299, 318`: in a manual throw, `g.throw` runs, then `events.add` raises, so `revision += 1` is skipped.
  - `server.py:353-358`: in a camera commit, `g.throw` and `revision += 1` run, then `events.add` raises, so `flow.close()` and `reset_base` are skipped.
- **Reproduced** with a recorder whose `events.jsonl` write raises ENOSPC. This is what a full disk or an unplugged external `--record` drive would do.
  - **Manual `/api/throw`:** the dart is recorded, the revision stays the same, and the reply is 500. The host's retry passes the revision check and records the dart a second time.
  - **Auto-commit** (`qa/autoloop.py`): one pending T20 became darts **[60, 60, 60]**, revision 0 → 3, within 2.5 s.
  - **`Recorder.stop()`** writes `recording_stopped` before it sets `active = False` (`recorder.py:102-103`). The write raises, so the recorder never stops, and every later write keeps failing.
- **Fix:**
  - Wrap the listener calls in `EventLog.add` in `try/except`.
  - In `Recorder.append`, catch `OSError`: mark the recorder inactive, set `error`, and close the files.
  - Call `app.flow.close(id)` before logging, and log only after the state change is complete.
  - Add a test with a failing listener.

### Q3 — Medium (M1-14). The frame writer dies silently.

- **Where:** `recorder.py:241-275`. `run()` and `write_new_frames()` have no exception handling.
- **Reproduced:** with an `OSError` on a frame write, the thread exits, but `status()` still reports `active: True` with `error: None`. The setup page shows "recording" while no footage is saved.
- **Fix:** catch the error in `run()` and call `stop(reason)`.

### Q4 — Medium (M1-12). A label that flickers between two values never auto-commits.

- **Where:** `camera_flow.py:49-56`. The proposal id is keyed on the label, so each label change gives a new id and a new `seen_at`.
- **What happens:** a near-wire dart whose label alternates (for example S20 ↔ S1) restarts the countdown on every change. An Accept tapped just before a flip gets 409.
- **Unit probe:** labels flipping every 0.3 s with a 0.5 s delay gave **0 commits in 3 s**.
- **Fix:** key the id on the blob (base generation + tip position within about 5 mm) and update the label in place. Or restart the countdown only when the dart moves.

### Q5 — Low

- **Undo while a camera dart is pending drops that dart.** `server.py:320` resets the base after an undo, so the pending detection becomes part of the empty-board image. Probe: dart 1 entered manually, dart 2 pending, Undo → no darts and no pending. Dart 2 must be re-tapped. The README (line 108) states this behaviour, but `/control` gives no warning. Possible fixes: skip the base reset on undo while a dart is pending, or show a notice.
- **After a bust, win or third dart, the pending chip reads "auto-accept in 0.0 s" forever.** `server.py:371` refuses the commit, but `flow.view()` still counts down. Show "turn over" instead.
- **`/api/record/disk` and `free_disk_bytes()` measure the wrong disk for `--record DIR`.** They measure `RECORDINGS_ROOT` (`server.py:86-88`), not the recording directory. The recorder's own guard uses the right path.
- **A disk-guard stop leaves the old listener registered.** The stop is started from `recorder.py:251`, which bypasses `stop_recording()`, so `recorder.match_event` stays in `app.events.listeners` (`server.py:105`). It is harmless because the method checks `active`, but listeners pile up.
- **`tools/eval_detection.py:446` still prints "--recording is not implemented (planned for M1-14)".** The replay was built as `tools/replay_recording.py` instead. That is a documented plan deviation, but the stub message is now misleading.
- **`make_labels` marks a corrected manual dart as `corrected` with `detection_label: null`** (`tools/make_labels.py:60-65`). Eval code must filter on `detection_label`, not on `source`.
- **Calibration, verify, mount-side and recording writes require `expected_revision` but do not bump it**, so another controller is not told about them. This is acceptable for one setup page.
- **`CameraFlow.closed` grows without bound** (`camera_flow.py:35`). About 100 entries per night, so it is a nit.
- **Readability:** `control.js` is still written as long one-line functions (for example `poll()` and `paintCamera()`). M1-09's 160-character line limit is exceeded throughout the new block.
